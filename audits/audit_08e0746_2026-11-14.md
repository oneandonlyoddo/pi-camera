# Repo audit — commit `08e0746` — 2026-11-14

**What this repo does:** It is the software for a home-built camera: a Raspberry Pi Zero 2 W with the HQ camera and a small touchscreen. It shows a live preview with an info overlay (the "HUD"), saves each photo as JPG and DNG (raw sensor data), and runs a small web page for the gallery, a remote shutter and gain/white-balance controls. A script copies code from the desktop to the Pi, and a test suite runs on the Pi.

**Load assumed:** one camera, one person, one or two phones on the home network. The limits are the Pi Zero's ~416 MB of usable RAM and its slow CPU, not the number of users.

Rule IDs (R1–R11) refer to `.claude/rules/`.

---

## Must fix

### 1. Three threads drive the camera at once (R2)
`digital_camera.py:112-126`, `touchscreen.py:84`, `digital_camera.py:177-236`

- **What this is:** The button and the touchscreen each run in their own thread (a part of the program that runs at the same time as the rest) and call `capture_photo()` directly. Meanwhile, the main loop reads camera metadata for the HUD, sends settings, and handles web captures.
- **Problem:** Picamera2 is not built for this. A tap during a web capture starts two mode switches at once, and the capture can fail or hang. Taps made during the ~10 s capture are handled afterwards, and each one becomes another photo. Two captures that start in the same second get the same filename, and the second overwrites the first (R11).
- **Fix:** The callbacks only set the request in `CameraState`. Make that request a `threading.Event`, and replace `time.sleep(HUD_UPDATE_INTERVAL)` in the loop with `event.wait(HUD_UPDATE_INTERVAL)`, so the loop wakes immediately (this also removes the up-to-1 s web delay). Drop requests that arrived during a capture. Add milliseconds (`%f`) to the timestamp so a name can never repeat.
- **If we skip it:** Fast or overlapping taps freeze or crash the camera, and photos can silently overwrite each other.

### 2. A photo takes 10 s, the JPG and DNG do not match, and the preview flips (R8)
`digital_camera.py:128-176`, `digital_camera.py:77`

- **What this is:** `capture_photo()` switches to full resolution twice (once for the JPG, once for the DNG), waits 0.5 s, and then builds a new preview config by hand.
- **Problem:** Measured on the device: ~10 s from trigger back to preview, ~5.5 s of it for the second exposure. The JPG and DNG are two different moments. The hand-built preview config lacks the 180° rotation, so the live preview is upside down from the first photo on (confirmed on the screen). Line 77 (`preview_config["format"] = "YUV420"`) has no effect; the device runs the preview as `XBGR8888`.
- **Fix:** One exposure: `request = self.camera.switch_mode_and_capture_request(still_config)`, then `request.save("main", jpg)`, `request.save_dng(raw)`, and `request.release()` in a `finally`. Delete the second capture, the 0.5 s pause, the manual `switch_mode` block (lines 164-172) and line 77. `switch_mode_and_capture_request` returns to the original preview config, rotation included. Keep `buffer_count=2`. Leave the still config without rotation; saved photos are already upright (the display, not the camera, is upside down).
- **If we skip it:** A slow camera, mismatched RAW files, and a preview that is upside down after the first shot.

### 3. The thumbnail URL can read and write outside the photo folder (R7)
`web/app.py:23-59`, `web/app.py:118-136`

- **What this is:** `/dcim/thumbs/<name>` builds a thumbnail from the name in the URL if none exists.
- **Problem:** The name is not checked. `curl --path-as-is http://<pi>:5000/dcim/thumbs/../../x.jpg` opens an image outside `DCIM/` and writes a JPEG into the project folder. `send_from_directory` would block the `..`, but the thumbnail function runs first. Anyone on the network can do this; there is no login.
- **Fix:** At the top of `generate_thumbnail_if_missing`, add `if Path(filename).name != filename: raise FileNotFoundError(filename)`. The `xfail` test `test_thumbnail_rejects_path_outside_dcim` then passes; remove its marker.
- **If we skip it:** Anyone on the network can make the Pi decode files of their choice and write files where nobody expects them.

### 4. Manual white balance turns photos green or magenta
`digital_camera.py:216-225`

- **What this is:** Setting a colour temperature disables automatic white balance and sets `ColourGains = (temp/4000, temp/4000)`, the multipliers for the red and blue channels.
- **Problem:** Red and blue always get the same gain, so the setting only moves the image between green and magenta, not between warm and cold. The slider allows 100 K → gains of 0.025 → almost no red or blue → a deep green photo. 8000 K → 2.0 / 2.0 → a magenta cast. This is reachable from the normal UI.
- **Fix:** On the Pi, check whether `ColourTemperature` is in `camera.camera_controls`. If so, send `{"AwbEnable": False, "ColourTemperature": temp}` and delete the formula. If not, take the red/blue pair for the temperature from the `ct_curve` in `/usr/share/libcamera/ipa/rpi/vc4/imx477.json`.
- **If we skip it:** Every photo with manual white balance has the wrong colours.

### 5. Settings from the web are not validated, and NaN loops forever (R7)
`web/app.py:146-174`, `digital_camera.py:198-233`

- **What this is:** `POST /api/settings` stores whatever `float()` / `int()` accepts.
- **Problem:** `{"gain": "nan"}` is accepted. NaN ("not a number") is never equal to itself, so `gain != self._last_gain` is true every second: the camera loop resends the controls every second and logs "Applied analogue gain: nan" forever. `{"color_temp": true}` becomes 1 K (a green photo, see 4). Negative values and gain 0.1–0.9 also pass. Invalid input is silently ignored instead of rejected.
- **Fix:** Range checks in the web layer using constants in `settings.py`: gain `0` or `1.0`–`16.0`, colour temperature `0` or `2000`–`8000`; reject non-finite values with `math.isfinite`; return `400` with a message. Set the slider minimums in `index.html` to match (Known issue 12). The `xfail` tests `test_settings_rejects_out_of_range` cover this.
- **If we skip it:** One bad request floods the log forever and leaves the camera in a broken state until a restart.

## Should fix

### 6. Paths depend on the folder the app is started from (R4)
`settings.py:23-24, 64, 81`, `digital_camera.py:35-36`, `hud.py:24`, `web/app.py:63-65`

- **What this is:** `PHOTOS_DIR = "DCIM"` and the HUD asset paths are relative to the working directory (the folder you are in when you start the program). Flask resolves them from the project folder instead.
- **Problem:** `python3 ~/workspace/pi-camera/main.py` run from the home folder saves photos to `~/DCIM`, the gallery stays empty, and the HUD loses its font and background. The service only works because it sets the working directory.
- **Fix:** `PROJECT_ROOT = Path(__file__).resolve().parent` in `settings.py`, and every path becomes `PROJECT_ROOT / "..."`. Delete the separate path handling in `web/app.py:63-65`. The four `xfail` tests in `tests/test_paths.py` cover this.
- **If we skip it:** Photos land in the wrong place whenever someone starts the app by hand.

### 7. Star imports hide a dependency, and ruff's autofix would break the HUD
`hud.py:4, 24`, `digital_camera.py:9`, `settings.py:6`

- **What this is:** `hud.py` and `digital_camera.py` use `from settings import *`, which pulls in every name from `settings.py`. `hud.py` gets `Path` only this way.
- **Problem:** ruff (the linter) marks `Path` in `settings.py` as unused, and `ruff check --fix` deletes it. `hud.py:24` then fails inside its `try`, and the HUD background silently disappears. This is also 50 of ruff's 56 findings, which bury real ones.
- **Fix:** `from pathlib import Path` in `hud.py`. Replace `from settings import *` in both files with `import settings` (`settings.NAME`) or explicit imports. Then `ruff check --fix` also removes the other unused imports (`main.py:11`, `touchscreen.py:3-4`).
- **If we skip it:** A routine cleanup silently breaks the HUD, and ruff stays too noisy to be useful.

### 8. The settings-to-camera logic has no test
`digital_camera.py:198-233`

- **What this is:** The code that turns gain and colour temperature into camera controls sits inside the camera loop.
- **Problem:** It only runs with a real camera, so no test covers it. That is why the NaN loop (5) and the green images (4) went unnoticed.
- **Fix:** Move the logic into a plain function `controls_for(gain, temp)` that returns the control dictionary, and add one test with 0, a normal value and a boundary value. The loop keeps only the change check and `set_controls`.
- **If we skip it:** The next settings bug only shows up in a photo.

### 9. Thumbnail code exists twice
`digital_camera.py:89-110`, `web/app.py:23-59`

- **What this is:** Two functions open a JPG, shrink it to 300×225 and save it with quality 85.
- **Problem:** They must always change together. The web version alone gets the safety check from 3 and the existence check.
- **Fix:** Keep one function `make_thumbnail(src, dst)` in a small shared module and call it from both places. Delete the other copy.
- **If we skip it:** The next thumbnail change gets made in one place only.

## Nice to have

### 10. The HUD loads its font file every second
`hud.py:69-72`

- **What this is:** `ImageFont.truetype(...)` runs inside `update()`, once per second.
- **Problem:** It parses the same font file every second on a slow CPU. The bare `except:` also catches Ctrl+C at that moment.
- **Fix:** Load the font once in `__init__`; use `except OSError`.
- **If we skip it:** A little wasted CPU every second.

### 11. The GPIO button is created even when it is turned off
`digital_camera.py:33-34, 116`

- **What this is:** With `GPIO_CONNECTED = False`, the code still claims GPIO 17 and only ignores the presses.
- **Problem:** It occupies a pin that nothing uses, and every press goes through an extra check.
- **Fix:** Create the `Button` only `if GPIO_CONNECTED`; remove the check in `button_pressed`; close it in `cleanup` only if it exists.
- **If we skip it:** A pin stays occupied for nothing (see "Not checked").

### 12. `requirements.txt` is not read by anything
`requirements.txt`

- **What this is:** A pip list, but the Pi installs packages via apt and the desktop does not run the app.
- **Problem:** Three package lists (README, CLAUDE.md, this file) must stay in sync, and they already differ (`python3-pytest` is missing here).
- **Fix:** Delete the file; remove it from rule R1 and the README. The apt line in the README is the single list.
- **If we skip it:** The lists drift further apart.

Left out: 2 smaller findings. When a capture fails, the web page still answers "ok". Photos are cached by the browser for a year, so a photo overwritten under the same name shows the old image.
