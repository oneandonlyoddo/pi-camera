# Repo audit — commit `690a5ee` — 2026-11-14

**What this repo does:** It is a camera app for a Raspberry Pi Zero 2W. It shows a live preview with an info overlay (the "HUD") and saves photos as JPG and RAW (DNG) files. A shutter button, the touchscreen, or a small Flask web page can take a photo. The web page also shows a photo gallery and lets you change gain and white balance. On a normal PC it uses the webcam instead.

**Load assumed:** one camera and one or two people using the web page on a home network. The limits that matter are the Pi Zero's 512 MB of RAM and its slow CPU, not the number of users.

---

## Must fix

### 1. Two triggers at once drive the camera from two threads
`digital_camera.py:112-126`, `touchscreen.py:84`

- **What this is:** The GPIO button callback and the touchscreen thread call `capture_photo()` directly. Meanwhile, the main loop calls `set_controls`, `capture_metadata` and its own `capture_photo`.
- **Problem:** Picamera2 is not safe to use from several threads at once. If you tap the screen while a web capture is running, two mode switches overlap. The capture can fail or hang, and the HUD's metadata call can block during the switch.
- **Fix:** Have the button and touch callbacks only set `camera_state.shutter_requested = True`. Then only the main loop touches the camera. To keep the shutter fast, make the flag a `threading.Event` and replace `time.sleep(HUD_UPDATE_INTERVAL)` with `event.wait(HUD_UPDATE_INTERVAL)`. The loop then wakes as soon as a trigger arrives. This removes code from both callbacks.
- **If we skip it:** Fast or overlapping triggers crash or freeze the camera, and you lose the shot.

### 2. Photos taken in the same second overwrite each other
`digital_camera.py:132-134`, `webcam_camera.py:79-80`

- **What this is:** Each file is named `IMG_YYYYmmdd_HHMMSS.jpg`.
- **Problem:** Two captures in the same second get the same name, and the second one silently replaces the first. Pressing SPACE twice in webcam mode is enough (it only pauses 0.2 s). On the Pi, a button press and a touch together also do it.
- **Fix:** Add `_%f` (microseconds) to the timestamp, or add `_1`, `_2` while the file already exists. One line.
- **If we skip it:** Photos are lost with no error.

### 3. The thumbnail URL can write files outside the thumbs folder
`web/app.py:33-52`

- **What this is:** `/dcim/thumbs/<path:filename>` builds file paths straight from the URL.
- **Problem:** `send_from_directory` blocks `..` (going up a folder), but `generate_thumbnail_if_missing` runs first and does not. A request like `curl --path-as-is /dcim/thumbs/../../x.jpg` makes the app decode an image outside `DCIM/` and write a JPEG into the project root. Anyone on the Wi-Fi can do this, because the web page has no login.
- **Fix:** At the top of the function, add `if Path(filename).name != filename: raise FileNotFoundError`. Do the same in `serve_photo` for clarity.
- **If we skip it:** Anyone on the same network can write files where they should not be able to.

### 4. Taking a photo resets the preview and saves it unrotated
`digital_camera.py:137-171`

- **What this is:** The preview is set up with `transform` (rotate 180°) when `PREVIEW_ROTATE` is on.
- **Problem:** The still config and the "back to preview" config do not include the transform. So with `PREVIEW_ROTATE = True`, the saved photos are upside down compared with the preview. After the first photo, the preview loses its rotation too. The manual `switch_mode(preview_config)` is also not needed, because `switch_mode_and_capture_*` already switches back to the previous config.
- **Fix:** Add the same `transform` to `still_config`. Delete lines 163-171 (the pause and the rebuilt preview config).
- **If we skip it:** A camera mounted upside down saves upside-down photos and shows a wrong preview after the first shot.

### 5. The JPG and the DNG are two different photos
`digital_camera.py:143-154`

- **What this is:** The code calls `switch_mode_and_capture_file` twice: once for the JPG, once for the RAW.
- **Problem:** That means two mode switches and two exposures. On a Pi Zero this takes several seconds, and anything that moves differs between the files. A RAW file is supposed to match its JPG.
- **Fix:** Capture once: `req = self.camera.switch_mode_and_capture_request(still_config)`, then `req.save("main", jpg_path)`, `req.save_dng(raw_path)`, and `req.release()`.
- **If we skip it:** Capture is about twice as slow, and the JPG and RAW do not match.

### 6. The white-balance slider does not set white balance
`digital_camera.py:222`

- **What this is:** It turns a Kelvin value into the red and blue colour gains (the "ColourGains" control).
- **Problem:** It sets red and blue to the same value (`temp/4000`). Real colour temperature moves them in opposite directions. With this code, 3000 K and 6000 K only shift the whole picture between green and magenta and change its brightness. They never make it warmer or cooler.
- **Fix:** Look up red and blue gains in a small table of a few points taken from the IMX477 tuning file's `ct_curve` (gain = 1/r, 1/b), and interpolate between them.
- **If we skip it:** Manual white balance gives wrong colours at every setting.

## Should fix

### 7. Settings input is not checked
`web/app.py:156-168`

- **What this is:** `POST /api/settings` turns the request values into numbers.
- **Problem:** `{"gain": "nan"}` is accepted. Because `nan != nan` is always true, the camera loop sends the bad gain to the camera every second, forever. Negative or very large values pass too. `{"gain": null}` raises a `TypeError` that is not caught, so the server returns a 500 error.
- **Fix:** Catch `(ValueError, TypeError)`, and return a 400 error unless `0 <= gain <= 16` and `0 <= color_temp <= 8000`.
- **If we skip it:** One bad request leaves gain stuck and fills the log with errors until you restart.

### 8. Gallery thumbnails can use up the Pi's memory
`web/app.py:46-52`

- **What this is:** When a thumbnail is missing, the server makes it on request.
- **Problem:** Each 4056×3040 JPEG takes about 37 MB of RAM once decoded. The Flask server answers requests in parallel threads, so opening the gallery on old photos can make 10 or more thumbnails at once, which is about 400 MB on a 512 MB Pi.
- **Fix:** Call `img.draft("RGB", (THUMBNAIL_WIDTH, THUMBNAIL_HEIGHT))` right after `Image.open`. The JPEG then decodes at 1/8 size, about 8 times faster and with 64 times less memory. One line.
- **If we skip it:** The first visit to the gallery can freeze or crash the Pi.

### 9. Half-written thumbnails can be cached for a year
`web/app.py:52`, `digital_camera.py:105`

- **What this is:** The camera and the web server can both write the same thumbnail file at the same moment.
- **Problem:** If the gallery asks for a thumbnail while the camera is still writing it, `thumb_path.exists()` is already true, so the server sends the half-written file. The browser then caches it with the 1-year header.
- **Fix:** Save to `thumb_path.with_suffix(".tmp")`, then rename it with `os.replace(tmp, thumb_path)`.
- **If we skip it:** Some gallery tiles stay grey or cut off until the browser cache is cleared.

### 10. Thumbnail code is copied three times
`digital_camera.py:89-110`, `webcam_camera.py:53-74`, `web/app.py:23-59`

- **What this is:** Three near-identical functions resize a JPG into `DCIM/thumbs/`.
- **Problem:** Fixes 8 and 9 would need to go into all three copies. Making the thumbnail at capture time also costs about a second of a 12 MP decode on the Pi Zero, every time you take a photo.
- **Fix:** Delete both copies in the camera classes and keep only `generate_thumbnail_if_missing`. The gallery always calls it before serving a thumbnail, and with fix 8 it is fast. About 45 fewer lines.
- **If we skip it:** Three places to keep in step, and slower captures.

### 11. The dev setup fails on Windows and Mac
`requirements.txt:2-5`

- **What this is:** CLAUDE.md says to run `pip install -r requirements.txt` on development machines.
- **Problem:** `picamera2` (it needs `python-prctl`) and `evdev` only install on Linux, so pip stops with an error on Windows and macOS.
- **Fix:** Add a platform marker to those lines: `picamera2>=0.3.33; sys_platform == "linux"`, and the same for `gpiozero` and `evdev`.
- **If we skip it:** Every new dev setup fails until someone edits the file by hand.

### 12. No tests for the web API
(no tests exist yet)

- **What this is:** The risky logic is the filename check (3), the settings bounds (7) and the shutter flag (1).
- **Problem:** If any of these breaks later, nothing will notice.
- **Fix:** Add one `test_app.py` that uses Flask's test client. It should check three things: `../` in a thumbnail URL returns 404, `{"gain": "nan"}` returns 400, and `POST /api/trigger` makes `consume_shutter_request()` return True once.
- **If we skip it:** The security fix can be undone by accident and nobody will know.

### 13. The GPIO button is created even when it is turned off
`digital_camera.py:33-34`

- **What this is:** `Button(...)` runs every time. `GPIO_CONNECTED` is only checked later, when the button is pressed.
- **Problem:** If the GPIO pins are not available (wrong user permissions, another program using pin 17), the constructor fails and the whole camera does not start, even with `GPIO_CONNECTED = False`.
- **Fix:** Only create the button when `GPIO_CONNECTED` is true. In `cleanup()`, close it only if it exists.
- **If we skip it:** A feature you turned off can stop the camera from starting.

### 14. Delete `capture_images_by_key.py`
(untracked file)

- **What this is:** An old standalone test script.
- **Problem:** Nothing uses it. It needs the `keyboard` package, which is not in the requirements. `key_flag` is set but never read, so holding P saves a new PNG on every loop pass.
- **Fix:** Delete it. 35 fewer lines.
- **If we skip it:** Readers think it is part of the app.

## Nice to have

### 15. The HUD reloads its font every frame
`hud.py:69-72`

- **What this is:** `ImageFont.truetype(...)` reads the font file from disk on every `update()`.
- **Problem:** In webcam mode, `update()` runs about 30 times a second.
- **Fix:** Load the font once in `__init__`. While there, add `from pathlib import Path`. Right now `Path` only works because `from settings import *` happens to bring it in.
- **If we skip it:** Slower preview in webcam mode. Changing `settings.py` silently disables the HUD background.

### 16. Webcam settings code that does nothing
`webcam_camera.py:132`, `webcam_camera.py:143-151`

- **What this is:** The colour-temperature branch only prints a message, inside a `try/except` that can never fail. The gain branch skips `gain == 0`, so moving the slider back to Auto does nothing.
- **Fix:** Delete the temperature branch (about 9 lines). If you keep gain, also handle the switch back to 0.
- **If we skip it:** Webcam mode behaves differently from the Pi when you go back to Auto.

### 17. The standalone web server runs in debug mode on all network interfaces
`web/app.py:187-189`

- **What this is:** `python web/app.py` starts the server with `debug=True` on `0.0.0.0`.
- **Problem:** That exposes the Werkzeug debugger, which can run code if someone gets past its PIN, to the whole network. In this mode the camera state is also empty, so the shutter returns a 500 error anyway.
- **Fix:** Delete the `__main__` block, and the `sys.path` hack with it. The app is always started from `main.py`.
- **If we skip it:** A small risk whenever someone runs the file directly.

3 smaller items are left out: the touchscreen state can get mixed up with multi-touch, the camera loop stops for good on its first unexpected error, and the `"format"` key on the preview config is probably ignored.

**Verdict:** Fix 1 and 2 first (they cause crashed captures and lost photos), then 3 and 4. All four are small changes.

**Lean:** -90 lines and 0 dependencies possible (fixes 10, 14, 16 and 17, plus the simpler callbacks in fix 1).

**Not checked:** Nothing was run, because there was no Pi hardware or `pi-cam` environment. The Picamera2 version installed on the Pi was not checked, so the API names in fix 5 assume version 0.3 or newer. The touchscreen was not tested against a real device, and `styles.css` and the uncommitted README changes were not read.
